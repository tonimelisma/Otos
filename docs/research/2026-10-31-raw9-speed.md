# RAW9 speed, and what a card waits on (2026-10-31)

## Question

Preparing a card for import regressed from 6.2 s to 70.5 s at #501 (`b4f1d3a`).
`docs/research/2026-10-31-card-render-timings.md` showed that time is spent in RAW9
developments on one serial lane. Can RAW9 itself be made fast enough? If not, what should
a card's first pass do instead?

## The regression, measured

Same Sony card (37 ARW, 37 HIF, 12 MP4), remounted cold, each build launched with an empty
dev catalog and nothing else running. The time is from launch until all 86 card rows had
enrichment stamps matching their files, which is what import planning waits on.

| Build | Card ready | Still thumbnails | At once (max) | ARW per file (median) | HIF per file (median) |
|---|---|---|---|---|---|
| `96cb4ae` (before #501) | 6.2 s | QuickLook | 8 | 330 ms | 315 ms |
| `b4f1d3a` (#501) | 70.5 s | `ImageRenderer` | 1 | 1,675 ms | 96 ms |
| `880eb97` (main) | 55.0 s | `ImageRenderer` | 1 | 1,302 ms | 106 ms |

QuickLook's thumbnail of an ARW is the camera's embedded JPEG. Its mean pixel difference
(0–255) was 1.6–3.8 from the embedded 1616 × 1080 preview on all 26 landscape ARWs, and
16–22 from Otos's RAW9 development. The 2026-10-25 research measured the same.

## Can RAW9 go faster?

Eight of the card's ARWs (ILCE-6700, 6192 × 4128, about 41 MB) were read into memory first,
then developed with `CIRAWFilter(imageData:)` at RAW9 and rendered to an RGBA8 Display P3
bitmap, as `ImageRenderer` does. Apple M1 Pro, 16 GB.

| Variant | Per file (median) | Wall per file |
|---|---|---|
| New `CIContext` per render (current), 2560 px | 1,127 ms | 1,256 ms |
| One shared `CIContext`, 2560 px | 1,099 ms | 1,274 ms |
| `draftModeEnabled`, 2560 px | 1,164 ms | 1,267 ms |
| Shared context, 256 px output | 1,098 ms | 1,066 ms |
| Draft mode, 256 px output | 1,110 ms | 1,054 ms |
| 2 at once, 2560 px | 1,908 ms | 1,074 ms |
| 4 at once, 2560 px | 3,983 ms | 1,476 ms |
| 4 at once, 256 px | 5,538 ms | 1,652 ms |
| 8 at once, 256 px | 5,153 ms | 1,127 ms |

**About 1.05–1.27 s per RAW, whatever the variant:**

- **The context.** Reusing a `CIContext` changes nothing measurable.
- **Draft mode.** Apple's header says it "can improve image decoding speed". On these files
  it does not.
- **Output size.** A 256 px output costs the same as a 2560 px one: the time is in decoding,
  not in output size.
- **Concurrency.** Two at once gains about 15% of throughput, and four is worse than one.

So RAW9 cannot be made fast enough for a card's first pass with the API Apple offers.

## Image I/O decodes do scale

Eight 12 MP iPhone HEICs, decoded to 2560 px as `ImageRenderer.decodeImage` does, 32 decodes
per run. The card's HIF files were not reachable because the card had been removed. These
files were taken from the local library, checked as not dataless.

| At once | Per decode (median) | Wall per decode |
|---|---|---|
| 1 | 181 ms | 177 ms |
| 2 | 179 ms | 106 ms |
| 4 | 288 ms | 71 ms |
| 8 | 531 ms | 69 ms |

## Conclusions

- **A card's first pass does not develop an unedited RAW.** Its thumbnail is QuickLook's,
  run by enrichment's eight workers, as before #501. It gets no preview.
- **Its library copy is developed.** Import reuse treats a RAW without a preview as a miss,
  so the copy is enriched from its own bytes after it lands. It then gets the RAW9 preview
  and thumbnail that ADR 0035 requires of a library still.
- **HEIF and other stills are unchanged:** developed during the card's first pass. The
  background lane now decodes four at a time and still develops RAWs one at a time.
