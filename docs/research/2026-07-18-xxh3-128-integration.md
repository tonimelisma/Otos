# XXH3-128 integration research — 2026-07-18

## Scope

Plan 0060 needs a stable, non-cryptographic content fact for image/video
primaries. The fact must be canonical across architectures, streamable from a
file, and small enough to remain subordinate overlay rather than identity.

## Primary upstream evidence

- [xxHash v0.8.3 release](https://github.com/Cyan4973/xxHash/releases/tag/v0.8.3)
  is the selected release. The checked-in vendor README records commit `e626a72`.
- [v0.8.3 source tree](https://github.com/Cyan4973/xxHash/tree/v0.8.3) supplies
  `xxhash.c`, `xxhash.h`, and the upstream license. Otos vendors only those build
  inputs plus local boundary code; it does not add the upstream CLI, benchmark
  suite, or test corpus to the app target.
- The [XXH3 family API reference](https://xxhash.com/doc/v0.8.3/group___x_x_h3__family.html)
  documents `XXH3_128bits`, the streaming reset/update/digest family, and
  `XXH128_canonicalFromHash`. Otos uses the default-seed streaming 128-bit path
  and converts the result before it crosses the C boundary.
- The [upstream test implementation](https://raw.githubusercontent.com/Cyan4973/xxHash/v0.8.3/tests/sanity_test.c)
  defines the stable pseudorandom sanity buffer used by the project tests. The
  canonical empty vector is `99aa06d3014798d86001c324468d497f`. The short
  vectors in `OtosTests/ContentHasherTests.swift` are independently cross-checked
  against [LLVM's published XXH3-128 sanity vectors](https://codebrowser.dev/llvm/llvm/unittests/Support/xxhashTest.cpp.html),
  including its `PRIME64`-generated byte prefix.
- The [xxHash project documentation](https://xxhash.com/) describes XXH3 as a
  high-throughput non-cryptographic hash. It is not used as an integrity or
  security claim in Otos.

## Integration decision

The smallest audited integration is the exact upstream C release behind a tiny
local C wrapper and one stateless Swift facade. Alternatives were considered in
ADR 0018: a Swift package wrapper, a new remote wrapper dependency, CryptoKit
SHA-256, and no stored hash. The chosen boundary keeps upstream layout and
endianness out of Swift domain code and stores only canonical 16-byte values.

## Chunk-size probe

The initial bounded chunk is 1 MiB. It is deliberately the simple sequential
path required by the plan; there is no buffer pool, mmap path, or extra worker.
`ContentHasherTests` exercises 0, 1, 1 MiB−1, 1 MiB, 1 MiB+1, and a multi-chunk
payload against a single-update reference through the same C boundary. The
configured local toolchain is Xcode 27 beta (`27A5218g`) with macOS deployment
target 27.0 on Apple Silicon.

## Runtime/performance evidence

The deterministic generated corpus was written outside media roots under
`/private/tmp/otos-0060-corpus` and hashed through the same local C boundary with
the 1 MiB read size. On the configured Apple M1 Pro / Xcode 27 environment, the
two-pass probe measured:

| Bytes | Cold MB/s | Warm MB/s |
| ---: | ---: | ---: |
| 0 | n/a | n/a |
| 1 | 0.50 | 0.50 |
| 1 MiB | 3,883.61 | 5,405.03 |
| 100 MB | 7,129.11 | 7,528.42 |
| 2 GB | 5,381.18 | 6,972.53 |

The 2 GB file was fully written, not sparse. The 0-byte timing is below the
clock's useful resolution; the 1-byte timing is likewise not a throughput claim.
The probe was intentionally a one-buffer sequential read and did not motivate a
pool, mmap path, custom copier, or second worker lifecycle.

The repository validation environment does not expose a usable CoreSimulator
service or a signed/running Otos process, so a real OneDrive sample and an
Instruments profile cannot be claimed here. The bounded tests provide deterministic
vector, boundary, cancellation, and open-failure evidence. The app build reached
Swift and C compilation when derived data was redirected to `/private/tmp`, then
the environment's CoreSimulator/Xcode service became unavailable. The remaining
runtime evidence is recorded as a non-blocking environment limitation in the DoD
report; no tuning or second hash lifecycle is introduced in response.

No digest values are emitted in diagnostics. Enrichment and import logs record
owner, byte count, elapsed milliseconds, throughput, cancellation, or typed failure
category, and the import timing record separates the hash span from copy, publish,
and settlement.
