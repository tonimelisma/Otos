# Otos Design System

Authoritative registry of **design rules** for user-facing surfaces. A row's
presence means Current. Retired rows are deleted (git history remembers).

This document is to visual and interaction design what `docs/requirements.md` is
to behavior: the thing a change is reviewed against. It does not describe screens.
Per-screen specs live beside it (`docs/design/import-bar.md`), and they cite these
IDs rather than restating them.

Otos uses Apple's semantic type styles, label colors, materials, and control
metrics as-is. Nothing here introduces a typeface or a palette. What it decides is
*which* semantic role each kind of Otos content gets, so hierarchy is a rule
rather than a per-screen judgement. Deviations from the platform default are
marked **[deviation]** and carry their justification inline.

Column meanings:

- **ID** — stable identifier (`DES-*`).
- **Rule** — the rule itself, stated so a reviewer can fail a change against it.
- **Check** — how to tell, by looking, that the rule holds.

## Principles

These are the design-side reading of the product invariants in `AGENTS.md`. When a
rule below and a principle here disagree, the principle wins and the rule is a bug.

- **Show the outcome, not the machine.** The user reads results and consequences.
  Internal vocabulary — plan, disposition, inventory, replan, companion, execution,
  queued — never reaches a progress label, even when it is the most accurate word
  available. A click that is accepted but held is acknowledged by disabling the
  control that took it, not by a label that names the holding.
- **One fact, one owner.** Any piece of state renders in exactly one place at a
  time. A second rendering is permitted only when the first is off-screen, and it
  is then smaller and quieter: an indicator, not a report.
- **Honest numbers, or none.** No denominator that can move, no percentage the app
  is guessing at. If a total is not yet known, state what is known and count up.
  This is `AGENTS.md`'s "do not fabricate" applied to labels.
- **Reassure rather than warn.** Originals are read-only and copies are additive,
  so almost nothing in Otos is dangerous. Alerts and destructive styling are for
  the few operations that actually destroy something.
- **The content is the interface.** Photographs carry the color. Chrome stays
  achromatic; the accent color marks only what to act on or what is selected.
- **Predictable before clever.** Where the platform has an answer, use it in its
  ordinary form. Custom behavior needs a reason that survives being written down.

## Type

macOS text styles are fixed sizes. Use the SwiftUI style name in code; never a
hard-coded point size.

| ID | Rule | Check |
| --- | --- | --- |
| DES-001 | Otos shall use the system font only. SF Mono is permitted in developer-facing surfaces (diagnostics, logs). No custom typeface shall be bundled. | Given source is inspected, no font file is bundled and no `Font.custom` call exists outside developer surfaces. |
| DES-002 | Otos shall use exactly seven text styles: `.title2` (17), `.title3` (15 semibold), `.headline` (13 semibold), `.body` (13), `.callout` (12), `.subheadline` (11), `.footnote` (10). Other styles are out of scope. | Given a view is inspected, every `.font(...)` call names one of the seven; no `.system(size:)` literal appears. |
| DES-003 | Role assignment shall be: `.title2` empty-state and sheet titles; `.title3` the primary fact of a status surface **[deviation: platform has no "status headline" role]**; `.headline` group headers inside content; `.body` the default for rows, control values, button titles, prose; `.callout` field labels beside a control; `.subheadline` secondary detail under a primary fact, and sidebar section headers; `.footnote` looked-up metadata. | Given a new string is added, it is assignable to exactly one of these roles without inventing an eighth. |
| DES-004 | A single surface shall use at most two weights (regular, semibold) and at most three of the seven sizes. Bold, italic, and manual letter-spacing shall not be used. The edit panel uses four sizes **[deviation: Photos and Lightroom set a section's title above its controls' names; with the file name above both and a RAW temperature's scale labels below, an inspector of folding sections needs four steps (DES-092)]**. | Given a bar, sheet, or pane, count weights and sizes. |
| DES-005A | Byte sizes shall be shown as whole KB below 1 MB (`840 KB`), whole MB from 1 MB (`68 MB`), GB with one decimal from 100 MB (`0.5 GB`, `4.2 GB`), and whole GB from 100 GB (`128 GB`). Item counts are exact and never abbreviated. The one exception: when the shown sizes of a duplicates group's copies tie but their bytes differ, its pictures show each size in the shown unit with the fewest decimals, up to three, that tell the copies apart (`39.13 MB`, `39.10 MB`), and exact bytes only when three still tie (DES-107). | Given any size string outside that exception, it carries at most one decimal place, and never a decimal on a kilobyte or megabyte figure. |
| DES-005 | Any number that changes in place shall use `.monospacedDigit()`: counts, byte totals, durations, sidebar item counts, progress figures. Text shall never reflow because a digit changed width. | Given an import runs, the status line's glyph positions do not shift as counts tick. |
| DES-006 | No user-facing text shall render below 10 pt. | Given any surface, the smallest text is `.footnote`. |

## Visual hierarchy

Three levels. Every user-facing string is assigned to one. Level is expressed by
**size and color together** — never by size alone, and never by weight alone.
**[deviation from an earlier draft: an ambient level was retired —
`DesignPalette` had zero real callers for it and no current surface shows ambient
metadata a user merely notices rather than reads;
inventing a caller for the unused level would have been a feature this app
doesn't have, not a design rule.]**

| ID | Rule | Check |
| --- | --- | --- |
| DES-010 | **L1 primary** — `.title3` semibold, `.primary` color. The answer to "what is happening" or "what will happen". Exactly one per surface. | Given a surface, exactly one string is L1. If the single primary fact cannot be named, the surface is not designed yet. |
| DES-011 | **L2 label** — `.body`, `.primary`. Things read to navigate or operate: row titles, control values, button titles. A group header inside content is L2 in `.headline` (the same size, semibold; DES-003). | — |
| DES-012 | **L3 supporting** — `.subheadline`, `.secondary`. Qualifies L1 and is optional by definition: if it disappeared the surface would remain usable. Field labels sit here. | Given L3 is hidden, the surface still states what it does and what the action is. |
| DES-014 | Adjacent levels shall differ in both size and color. Two items at the same level, side by side, shall be separated by space or a hairline — never by a size tweak. | — |
| DES-015 | Proximity: a number and the control acting on it shall be within 8 pt, or the number shall be inside the control's title. | Given a count and its action button, measure the gap or read the title. |
| DES-016 | Alignment: field labels within a group shall share a left edge and a fixed label-column width. No centered text in chrome. | Given a group of labelled controls, one vertical edge runs through all labels. |
| DES-017 | Repetition: the same relationship shall look the same everywhere — label left, control right, 7 pt gap — across every surface in the app. | Given two different surfaces with labelled controls, the metrics match. |
| DES-018 | A status surface shall read left to right as *what* (L1 over L3) · *choices* (behind a hairline) · *the act*. Zones shall not swap sides between states, and the surface shall keep one fixed height across all states. | Given a state change, nothing above the surface reflows and no zone moves. |

## Color

Semantic roles only. Values below are documentation, not constants to paste into
view code. Both appearances are first-class; every surface is reviewed in both.

| ID | Rule | Check |
| --- | --- | --- |
| DES-020 | View code shall name colors semantically — the platform's own (`.primary`, `Color.accentColor`, system materials) or one of Otos's named app-level semantic colors. No literal hex, RGB, or opacity-on-a-color value shall appear in a view. Otos defines its own values in exactly two places, both marked deviations: the text values of DES-021 and the chrome values of DES-022. Those definitions live in one palette type, `Otos/Views/DesignPalette.swift`, carry both appearances, and are the only place a literal is written — `guard-design-system.sh` allowlists only that file. | Given a view is inspected, no color literal exists and every non-platform color resolves to a named palette member. |
| DES-021 | Text colors shall be: label 85% (L1, L2); 60% black light / 60% white dark (L3) **[deviation: the system secondary label values measure 3.9:1 on Otos's lighter chrome and fail the text minimum — see `hig-validation.md` F-1]**. The `.tertiary` semantic value is reserved for non-text elements, where the 3:1 non-text minimum applies. | Accessibility Inspector on L1, L2, and L3 in both appearances. |
| DES-022 | Surface order shall be, light: content `#FFFFFF`, sidebar `#FAFAFB`, bar `#FBFBFC` **[deviation: lighter than the default window gray — the app's content is photographs, and a mid-gray chrome competes with them for the eye]**; dark: content `#1C1C1E`, sidebar `#242426`, bar `#2A2A2C` (bar brighter than content, per platform elevation order). The order governs **chrome** over content. A surface that floats but is not chrome takes the `content` value: the grid's day bar is a copy of a section header held at the top edge (DES-069), and giving it a chrome value is what made it read as an unrelated band rather than as the label it duplicates. The Loupe and Compare panes are content too: their backdrop is `content` in every state — placeholder, upscaled thumbnail, full decode, and inline video alike — so the arrival of a sharper decode changes only the image, never the surface around it. | Given both appearances, chrome is distinguishable from content by value alone with no border needed; given a Loupe pane showing an upscaled thumbnail and then its full decode, the letterbox around the image is the same `content` value before and after. |
| DES-023 | Separators shall be hairlines at 8% black / 10% white **[deviation: system separator is ~13% — at the reduced chrome contrast of DES-022 a 13% line reads as a drawn rule rather than a seam]**. Under Increase Contrast they revert to the system separator strength. | — |
| DES-024 | The accent color shall be the user's system accent, used only for: selection, the single prominent button, focus rings, determinate progress. It shall never be a decorative tint nor a fill larger than a control; the platform's own on-state of a checkbox or radio button is a fill no larger than the control. | Given a surface, every accent-colored pixel is selected, actionable, or progress. |
| DES-025 | Green shall mean completion that has been *verified*, and nothing else: a checkmark on a filled circle, 22 pt, once per completed operation. Not "on", not "healthy". | — |
| DES-026 | Orange shall mean needs attention with nothing lost — unreadable files, unavailable library, skipped items — and shall always be paired with a way to look at the thing. | Given an orange indicator, an adjacent control reveals the affected items. |
| DES-027 | Red shall be reserved for destruction: erasing a card, removing a library. Per HIG, a destructive action the user deliberately chose is not styled red; red is for the one they might hit by accident. | — |
| DES-027A | A destructive per-run option shall be presented as a control on the surface that performs the action, pre-set from its durable Settings preference **[owner decision, 2026-08-13: card erase keeps its sticky Settings preference, and that preference is the default value of the pre-flight checkbox in the bar]**. Changing it in the bar applies to this run only. The checkbox's own title is the statement of consequence; it shall not be restated as prose. Where the destructive action runs *alone* — no copies, only deletion — it shall confirm with an alert stating the exact count, with verb titles (DES-036). | Given an erase-only run, an alert names the number of items to be deleted; given an ordinary import with erase checked, no extra prose appears. |
| DES-028 | Contrast shall be at least 4.5:1 for L1, L2 and L3 — all Otos text is below the 18 pt / 14 pt-bold large-text threshold, so the relaxed 3:1 large-text allowance never applies — and at least 3:1 for non-text elements that carry meaning. Both appearances are measured, not assumed. Measured values are recorded in `hig-validation.md`. | Accessibility Inspector, light and dark, on every text level of the surface. |
| DES-029 | No information shall be carried by color alone. The attention badge carries a glyph, completion carries a checkmark, selection carries a border as well as a tint. | Given a grayscale screenshot, every state remains distinguishable. |

## Status and copy

Every long-running operation — scan, enrich, import, reorganize — exposes the same
three user-facing states regardless of how many internal states it owns. Two
further states exist only because they are actionable: *needs attention* and
*failed*.

| ID | Rule | Check |
| --- | --- | --- |
| DES-030 | While an operation is being prepared or is running, its user-facing status shall collapse to **Preparing**, **Working**, **Done**, plus **Needs attention** and **Failed**. A surface may additionally rest in states where no operation exists — nothing to do yet, ready to start, or missing a prerequisite the user must supply; those are not operation status and are not counted against the five. Internal state names shall not be published, and the count of user-visible states shall not grow with the count of internal states. | Given an operation's states are listed in code, the strings describing a prepared or running operation number five or fewer, and every additional surface state is one where no operation exists. |
| DES-031 | Preparing shall use the present participle and keep its primary action visible and disabled. Its indicator shall be **determinate whenever an honest denominator exists**, counting up beside it ("112 of 181 items"), and indeterminate only before one does — while enumeration is still running and no real total is knowable. Once determinate, it shall not fall back to indeterminate for the rest of the stage: a rebuild that has no new count yet keeps showing the last proven one. The rule is that the bar's indicator reports the progress of the stage the bar is in, so preparation progress is drawn while preparing exactly as execution progress is drawn while working. | Given preparing with enumeration finished, the indicator is determinate and a count is shown; given enumeration still running, it is indeterminate with no count; given a re-plan mid-preparation, the indicator stays determinate and the count does not blank. `Otos/Views/ImportBarPresentation.swift`, `Otos/Services/MediaOperationCoordinator.swift` |
| DES-032 | Working shall use a determinate indicator with items at L1 and bytes plus remaining time at L3, and shall offer Cancel whenever cancelling is safe — labelled `Cancel`, with no confirmation, because copies are additive and originals are read-only. The indicator shall expose its real value and total; a percentage shall not be displayed unless both are known, and shall never be synthesized from an estimate. Remaining time is the one permitted estimate, because it answers a question no measured value can: it shall be derived only from bytes actually transferred over elapsed time in the current run, shall always be hedged (`about 40 seconds left`), shall be stated in units a person reads with precision degrading as the estimate grows — seconds below a minute, whole minutes below an hour, hours and minutes above, never a raw second count like `about 221 seconds left` whose trailing digits change every tick while carrying no information the rate supports — and shall be omitted — not guessed — until enough of the run has completed for the rate to be meaningful. | Given an import, a determinate bar advances, Cancel is present, no invented percentage appears, and the time estimate is absent at the start of the run rather than wildly wrong. |
| DES-033 | Done shall use the past tense and shall state the guarantee, not the plan ("42 items copied and verified"), then where the result went, then a way to go there. | — |
| DES-034 | A status string shall contain one clause and at most one middot separating two facts of equal rank. A third fact requires a second line or a different level. Em-dash chains shall not be used. A line of looked-up facts under a group header (DES-107) is not a status string: it carries up to five facts a middot apart and omits a fact the catalog lacks. A legend — the one explanatory sentence a bar's middle zone shows while it has nothing to report — and a duplicates header's decision line are prose, not status strings. | Count middots and clauses per line. |
| DES-035 | User-facing nouns shall be the ones the user owns: items, photos, videos, card, library. Domain nouns — plan, disposition, companion, preexisting, blocked, execution, inventory — shall not appear. | Grep the string catalog for the forbidden set. |
| DES-036 | Button titles shall be verb phrases naming the result: `Import`, `Eject Card`, `Erase 181 Items`. A title carries a count only when the count is the new information the click commits to — a destructive act, or a subset the user chose — never when it repeats the surface's primary fact: Otos imports everything new, so `Import` says all there is to say and the number is L1's. `OK` shall not be used on a consequential action. | Given a surface with a count at L1, the primary button does not restate it; given an erase-only run, the alert and the button both carry the count. |
| DES-037 | Copy shall be sentence case, except button titles and menu items, which take title case per macOS. | — |
| DES-038 | An unactionable invariant shall never be stated as prose. Where a rule blocks a control, disable the control and explain it in that control's tooltip. | Given a withheld capability, the explanation lives on the disabled control, not in a status line. |
| DES-039 | Build, roadmap, and implementation status shall never appear in user-facing copy. | Grep for "later update", "not yet implemented", "coming". |
| DES-040 | A status surface at the bottom of the content pane owns the operation belonging to the current selection. The one exception is the trash queue (DES-089), which belongs to no selection and therefore shows in every scope, below the selection's own surface. A sidebar row may show a small indicator only for an operation whose surface is not currently visible. The toolbar shall never carry operation status. | Given a card is selected and its bar is visible, its sidebar row shows no spinner. |
| DES-041 | Sheets are for a scoped task with an explicit Cancel. Read-only inspection shall use a panel or inline disclosure, never a modal sheet. A lone `Done` shall not be the only exit. | — |

## Metrics and controls

A 4 pt base unit. Permitted spacing steps: 2, 4, 7, 8, 12, 16, 20, 28. Radii: 4
tile, 6 small control, 7 push button, 9–11 window and card.

| ID | Rule | Check |
| --- | --- | --- |
| DES-050 | Spacing shall use only the permitted steps; radii only the permitted values. | Given a view, every padding and spacing value is in the set. |
| DES-051 | Push buttons shall be 30 pt in a bar and 24 pt in dense inspectors; popups and small controls 22 pt; checkboxes 14 pt with a 12 pt label. Minimum click target 28×28 including padding. | — |
| DES-052 | At most one prominent button per surface, and where one exists it shall be the one Return fires. A surface that is pure report — nothing left to decide, nothing left to act on — may carry none rather than promote a control whose effect the user already has (the import bar's incomplete Done state, `docs/design/import-bar.md`). **[deviation]** The duplicates bar's bulk move is a plain bordered button with no Return equivalent: Return opens the selected group, and a bulk move of marked copies must not be one keystroke from a list (`docs/design/duplicates.md`). | Given a surface, count `.borderedProminent` uses: never more than one, and where there is one, Return fires it. |
| DES-053 | A disabled primary action shall keep its position and its title. Controls shall not appear and disappear between states of the same surface, and the surface's height shall be constant across states — a state whose middle zone is empty holds blank space rather than shrinking. The one exception: a control whose subject no longer exists may be omitted (the destination pop-up on an empty card, where there is nothing to copy); a control that is merely unavailable is disabled, not removed. | Measure the surface's height in every state — one value. Given an empty card, the pop-up is absent; given attention items, the erase checkbox is present and disabled. |
| DES-054 | Per-operation decisions — destination, eject, erase — shall sit next to the action that consumes them, each pre-set from its durable Settings preference (DES-027A). A mutually-exclusive choice shall use a pop-up button, and that pop-up button shall carry an introductory label naming what is being chosen, per HIG: a bare value gives no way to predict the menu's contents. A two-state choice shall use a checkbox, not a toggle button. | Given the import bar, every per-run decision is present inline, and the destination pop-up has a label. |

## Grid and tiles

| DES-066 | Curation uses one two-act toggle group — `hand.thumbsup` and `hand.thumbsdown`, outline at rest and filled when carried — over the three user-facing states Liked, Not Rated, and Disliked. | DES-068 | Curation is never color-only. The glyph stays at full contrast in both states. | Given grayscale or Increase Contrast, outline and filled remain distinguishable from each other, the selected act reads as no less prominent than the unselected one, and the active Compare target remains distinguishable. |
| DES-069 | A grid shall be grouped into day sections, each headed by a `.headline` date and a `.subheadline` count that scrolls with its own run, and a day bar at the top of the scroll area shall carry a copy of that label for whichever day owns the viewport's top edge — so a date is on screen at all times.
